# 0001. Operator identity via `app_session`

- Status: accepted
- Date: 2026-09-27

## Контекст

FR-10 требует, чтобы каждая запись `audit_log` называла оператора (имя + роль), а FR-01 — чтобы правка закрытого рейса требовала отдельного права и причины, которая тоже уходит в аудит. `audit_log` заполняется исключительно SQL-триггерами (`0002_audit_triggers.sql`) — сервисный код не пишет в него напрямую (`CLAUDE.md` «Аудит — автоматический»). Триггеру, чтобы подставить актора, нужен источник, доступный из тела `BEFORE`/`AFTER`-триггера на любой из восьми аудируемых таблиц, включая `DELETE` (где `NEW` недоступна). Продукт офлайновый, однопользовательский на одном судовом ПК за раз (FR-13), без пароля и сервера аутентификации (FR-10 explicitly excludes это для MVP).

## Решение

Персистентная таблица `app_session` (`0003_operator_context.sql`) с ровно одной строкой (`id INTEGER PRIMARY KEY CHECK (id = 1)`): `operator_name`, `operator_role`, `override_reason`. `SessionService.start()` делает `INSERT OR REPLACE` при каждом входе в приложение. 24 триггера аудита переписаны так, что вместо литерала `NULL` в `user_id`/`user_role`/`reason` подставляется `(SELECT ... FROM app_session WHERE id = 1)` — работает в любом триггере, включая `DELETE`, и на любом из соединений пула, потому что строка живёт в самой базе, а не в памяти процесса.

## Альтернативы

1. **TEMP-таблица или `PRAGMA`/session-переменная.** Состояние TEMP-таблицы и большинства `PRAGMA` привязано к конкретному соединению SQLite и не переживает возврат соединения в пул `tauri-plugin-sql` — следующий запрос на другом соединении из пула увидел бы актора предыдущей сессии или пустоту. Отвергнуто.
2. **Bind-параметр актора в каждый INSERT/UPDATE/DELETE.** Работает для `INSERT`/`UPDATE`, но `DELETE`-триггер не может взять актора из удаляемой строки — параметр пришлось бы протаскивать отдельным каналом, а восемь аудируемых таблиц пришлось бы расширять служебной колонкой ради данных, которые не относятся к бизнес-модели строки. Отвергнуто.
3. **Полноценная аутентификация (логин/пароль, серверная проверка).** Прямо исключена FR-10 для MVP: продукт офлайн-первый (FR-13), работает на судовом ПК без сервера; полноценная ролевая матрица и пароль — в «Отложенном» `Plans/01`. Отвергнуто как избыточное для однопользовательского судового приложения.

## Последствия

- Идентичность актора одна и та же для «кто изменил» (FR-10) и для права правки закрытого рейса (FR-01) — не два механизма, а одна пара имя+роль (`Requirements/fr.md` FR-10, «Открытые вопросы» п.1).
- `withVoyageGuard` читает и очищает `app_session.override_reason` **вне** транзакции статемента-мутации (автокоммит) — так порядок `await` остаётся детерминированным даже если гипотеза 11 (два соединения на один запрос) окажется актуальной где-то ещё; обрыв между set/clear лечится следующим `SessionService.start()`.
- Смена оператора между действиями внутри одной сессии приложения невозможна без повторного входа — соответствует FR-10 «указываются при запуске», не подходит для сценария передачи ПК другому человеку без перезапуска (не встречался в сценариях S-1..S-14).
