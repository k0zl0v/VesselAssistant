# 0003. Test pyramid and the hand-written IPC bridge

- Status: accepted
- Date: 2026-09-27

## Контекст

До этой ветки автотесты стояли на двух уровнях (`calc`, `service+SQLite`, обе — без Tauri) плюс ручная проверка глазами. Приоритетные сценарии S-1/S-4/S-7/S-13 требуют доказательства «UI → сервис → SQLite одним прогоном» — то есть реального рендера React-компонентов поверх настоящей сборки и настоящего IPC-канала, а не мока сервисного слоя. `Research/04` (debate skeptic vs advocate, 3 итерации) разбирал варианты для этого уровня и отдельно для Windows-специфичного пути (`execute_batch`, `plugin-fs` capability scope, файловый лог).

## Решение

- **e2e (Linux/CI, Playwright).** Честная сборка (`vite preview`) + рукописный мост `e2e/tauri-bridge/{init-script,node-side,install}.ts`, инжектирующий `window.__TAURI_INTERNALS__` с той же сигнатурой, что и настоящий Tauri рантайм (три аргумента `invoke`, включая `options` с `headers`, — то, что теряет документированный `mockIPC`). `bridge-contract.test.ts` прогоняет реальный клиентский код из `node_modules` (`@tauri-apps/api`/`plugin-sql`/`plugin-fs`/`plugin-dialog`/`plugin-log`) против моста и падает на любом расхождении формы ответа.
- **windows-smoke (Windows-only, CI).** `tauri-driver` + `msedgedriver` управляют настоящим собранным приложением (`npm run tauri build -- --debug --no-bundle`) — единственный уровень, где реальный Rust-хост, реальный WebView2 и реальные capability-права проверяются вместе.
- **Фикстура импорта — реальный XLSX**, сгенерированный `scripts/generate-import-fixture.ts` из `src/fixtures/kavkaz-iv.ts` (те же контрольные числа, что в Appendix C) и закоммиченный, а не собранный вручную байт-в-байт синтетический файл.

## Альтернативы

1. **`mockIPC` (документированный Tauri API для тестов).** Теряет третий аргумент `invoke` (`options`), в котором `@tauri-apps/plugin-fs`'s `writeTextFile`/`writeFile` несут путь и опции файла через `headers` — без него запись файла в тесте не воспроизводима тем же кодом, что в проде. Отвергнуто.
2. **Держать e2e-уровень целиком на моках сервисного слоя (Vitest + jsdom, без реального IPC).** Не различает «форма показывает то, что нужно» от «форма вызывает правильный сервис» — не даёт того самого доказательства «UI → сервис → SQLite одним прогоном», которое сценарии S-1/S-4/S-7/S-13 требуют явно. Отвергнуто как не отвечающее собственному критерию сценария.
3. **Обходиться без Windows-специфичного уровня, полагаясь на Linux e2e + `cargo test`.** Оставило бы непроверенными ровно те вещи, что специфичны для Windows и capability-модели: реальные права `plugin-fs` (гипотеза 10), реальный `execute_batch` на настоящем пуле, реальный файловый лог. Отвергнуто — это ровно то, что задание прямо требует подтвердить/опровергнуть эмпирически, не косвенно.
4. **Синтетический/собранный вручную XLSX-фикстура вместо реально сгенерированного файла.** Не гарантирует байтовую форму, которую реальный Excel-экспорт производит (стили ячеек, типы, структура листов) — риск, что тест проходит на файле, непохожем на то, что реально попадёт в руки оператора. Отвергнуто в пользу генератора из тех же контрольных данных, что использует regression-baseline.

## Последствия

- **macOS webview — пробел, не закрытый ни одним автоматическим уровнем.** `tauri-driver` для macOS требует `WebKitWebDriver`, который на практике куда менее стабилен и не покрыт тем же CI-путём, что Windows — решение сознательно не пытается закрыть этот пробел автоматизацией. Компенсация: ручной `npm run tauri dev` перед релизом (шаг 23 плана) + `cargo test` на `macos-14` внутри `release.yml` (проверяет только Rust-слой, не сам webview).
- Мост `e2e/tauri-bridge/**` — код, который нужно поддерживать в синхроне с реальными IPC-контрактами; `bridge-contract.test.ts` — единственная защита от расхождения, и её обязательность не опциональна при добавлении новой IPC-команды.
- Windows-smoke — единственный уровень без Linux-эквивалента. Он гоняется на каждом PR и push в `main`, где изменён хоть один файл вне чистой документации (`changes.rust` — deny-list `**/*.md`/`.claude/**`/`.vscode/**`/`.gitignore` с `predicate-quantifier: 'every'`, см. `.github/workflows/ci.yml`), плюс ночной `schedule` и ручной `workflow_dispatch`. Пропускает его только PR из одной документации, а такой PR не меняет ничего, что собирает `tauri build`, — Windows-регрессия, внесённая кодом PR, ловится на самом этом PR.
