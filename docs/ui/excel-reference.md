# Что показал исходный Excel

Разбор рабочего файла `Kavkaz IV_ Load St Plan+SOF.xlsx` (скриншоты от
04.10.2026). Все числа ниже сверены скриптом с `src/fixtures/kavkaz-iv.ts`
и сходятся до третьего знака — расхождений в расчётах нет, но **предметная
модель шире, чем та, что сейчас в коде**.

Этот файл — источник правды по тому, как операторы реально работают.
При противоречии с `CLAUDE.md` побеждает он; при противоречии с ТЗ —
побеждает ТЗ, а расхождение выносится в «Открытые вопросы».

## 1. OGV — это океанское судно, а не журнал

`CLAUDE.md` расшифровывает OGV как «operational goods-vessel log —
операционный журнал». Файл говорит другое: **OGV = Ocean Going Vessel**,
океанское судно под погрузкой на рейде.

Доказательства из листа `OGV`:

- Заголовок блока: `CARGO PLAN m/v "AAI PRELUDE" — 58 754,045 mt / 69 000,000 mt`.
- Колонки `Hold №7 … Hold №1` — у AAI PRELUDE семь трюмов, у KAVKAZ IV пять.
- Два источника: `KAVKAZ IV Transshipment from barges` (баржа KAVKAZ III,
  56 753,045 т) и `From Cargo Holds m/v Kavkaz IV` (2 001,000 т).
- ТЗ §3 это подтверждает: «распределение по трюмам №1-7, начало/окончание,
  остатки к загрузке по sequence plan».

Схема сходится точно:

| | т |
|---|---:|
| Из барж (KAVKAZ III) | 56 753.045 |
| Из трюмов KAVKAZ IV | 2 001.000 |
| **Погружено в AAI PRELUDE** | **58 754.045** |
| Cargo plan (7 трюмов) | 69 000.000 |
| Remains to load | 10 245.955 |

Привязка пооперационно: выгрузка 1 177,000 из трюма №3 KAVKAZ IV ушла в
трюм №2 OGV; 824,000 из трюма №5 — в трюм №5 OGV
(6 938,661 из барж + 824,000 = 7 762,661 ✓).

Два трюма OGV загружены **сверх плана**: №4 на −4,140 и №1 на −64,270.
Это и есть «отрицательный остаток» из ТЗ §8.3 — в реальном файле он
встречается штатно и подсвечен красным.

**Следствие для кода:** `OgvService` сейчас умеет только выгрузку из трюма
KAVKAZ IV. Не хватает самой сущности принимающего судна с его трюмами,
cargo plan и sequence plan, а также поступлений из барж, минуя KAVKAZ IV.

## 2. Крановая поправка — отдельный рабочий лист смены

Это самое крупное расхождение. В коде `CRANE_OPERATION_TYPES =
['loading', 'discharging', 'shifting']` плюс `side: PORT | STARBOARD | BOTH`.
В файле — **четыре режима работы**, и они не раскладываются на эту пару:

| Режим в файле | Смысл | Деление по бортам | Ближайший тип в коде |
|---|---|---|---|
| `ИЗ СЕБЯ` | выгрузка из своих трюмов | нет | `discharging` |
| `ПРЯМА` (прямой вариант) | баржа → OGV, минуя трюмы | нет | **типа нет** |
| `В СЕБЯ` port side | погрузка в свои трюмы, левый борт | да | `loading` + `PORT` |
| `В СЕБЯ` st. side | погрузка в свои трюмы, правый борт | да | `loading` + `STARBOARD` |

`shifting` в файле не встречается ни разу.

Каждый режим ведётся по двум кранам. Замеры из файла и проверка формулы
`correctedWeight = scale / coefficient`:

| Режим | Кран | По весам | k | Скорректировано | В файле |
|---|---|---:|---:|---:|---:|
| ИЗ СЕБЯ | 1 | 1 177 | 1.06 | 1 110.377 | 1110 |
| ИЗ СЕБЯ | 2 | 824 | 0.96 | 858.333 | 858 |
| ПРЯМА | 1 | 2 154 | 1.13 | 1 906.195 | 1906 |
| ПРЯМА | 2 | 610 | 1.04 | 586.538 | 587 |
| В СЕБЯ л/б | 1 | 1 387 | 1.06 | 1 308.491 | 1308 |
| В СЕБЯ л/б | 2 | 604 | 1.01 | 598.020 | 598 |
| В СЕБЯ п/б | 1 | 1 269 | 0.98 | 1 294.898 | 1295 |
| В СЕБЯ п/б | 2 | 810 | 1.09 | 743.119 | 743 |

Формула в коде верна. Итог за смену: 8 835.000 по весам → 8 405.971
скорректированных, поправка −429.029 т.

**Вес по весам «ИЗ СЕБЯ» = 1 177 + 824 = 2 001,000 — ровно `Discharged` в
Load Plan.** То есть в остатки трюмов списывается **вес по судовым весам**,
а скорректированный живёт отдельной строкой и на `remain` не влияет.
Это важно: попытка «починить» расчёт, подставив скорректированный вес в
остатки, сломает сходимость с контрольным файлом.

### Коэффициент выводится из истории замеров

Справа от каждого режима — история: `(судно, дата, коэффициент)`. Часть
значений помечена красным и в расчёт не идёт. Пример `ПРЯМА / Кран 1`:

```
GAMMA        14.02.2025   1.07
Lubov        09.08.2025   1.10
Шилайняй     17.08.2025   1.10
Anastasia V  27.08.2025   1.178
Lydia V      28.08.2025   1.13
I. Vikulov   19.10.2025   1.39   ← красный, выброс
                          -----
среднее по включённым     1.116   (в файле 1,115)
принят в работу           1.13
```

Среднее по невыброшенным сходится (1.116 ≈ 1.115), **но не везде**: у
`В СЕБЯ п/б / Кран 2` среднее по всем шести замерам даёт 0.935, а в файле
принято 0.97. Значит рабочий коэффициент — не механическое среднее, а
решение оператора. В макете так и сделано: среднее считается и показывается,
но принятое значение редактируется отдельно.

**Следствие для кода:** таблица `crane_coefficients` хранит плоский список
с `valid_from` / `valid_to`. Нет понятия «замер», нет флага исключения из
расчёта и нет связи «история → принятый коэффициент». Нужна либо вторая
таблица `crane_measurements`, либо флаг `excluded` + `is_working` на
существующей.

## 3. Профиль судна и две величины, которых нет в UI

Главный лист — это рисунок судна: трюмы `CH №5 … CH №1` слева направо
(корма слева, нос справа) и два крана над ними. Под каждым трюмом:

```
SFM
V = 44,7 %
Approx Volume = 5959,105 m3
```

- `V` — **процент заполнения по объёму**. Это `100 − emptyVolumePercent`;
  `calc/capacity.ts` считает обратную величину, и в UI сейчас выводится
  только она («Пусто, %»). Оператор же читает заполнение.
- `Approx Volume` — **свободный объём в м³** = `volume − remain × SF`.
  Сверено по всем пяти трюмам, сходится точно (4 462.42 / 2 515.802 /
  6 681.8 / 3 383.81 / 5 959.105). В интерфейсе этой величины нет вообще,
  хотя она отвечает на главный вопрос погрузки: влезет ли ещё.

Оба значения вынесены в макете в полосу «Профиль судна» над таблицей.

### SF хранится в двух единицах

В листе SF записан парой: `51 | 1,44` и `44 | 1,23`. Первое — ft³/т,
второе — м³/т (51 ft³ ≈ 1.444 м³). В коде только м³/т. Плюс в листе для
пшеницы показано `1,23`, а в фикстуре `1.226` — это округление
отображения, а не другое значение.

## 5. SOF — это Standard Time Sheet

Лист SOF состоит из двух частей, в коде представлена только вторая.

**Шапка — 18 нумерованных полей** печатной формы: 1. Shipping Co,
2. Vessel's name, 3. Port, 4. Owners, 5. Vessel berthed, 6. Loading
commenced, 7. Loading completed, 8. Cargo, 9. Discharging commenced,
10. Discharging completed, 11. Cargo documents on board, 12. Vessel sailed,
13. Charter Party, 14. Bill of discharge weight, 15. NOR tendered,
16. Vessel arrived at road, 18. NOR accepted. Десять из них — временны́е
вехи, и их значения выводимы из журнала событий; остальные берутся из
справочников и карточки рейса.

**`Details of Daily Working`** — таблица `Date / From / To / описание` плюс
две колонки, которых нет в `SofEvent`: **`Disch 24hrs`** (выгружено за
сутки) и **`Totall disch`** (нарастающим итогом). Строки разделены
жёлтыми строками-разделителями по суткам.

Подтверждается и обработка `24:00`: в файле есть
`17:00 → 24:00` и продолжение `00:00 → 24:00` следующими сутками —
`calc/time.ts` это уже умеет.

## 6. Мелочи, замеченные попутно

- Внизу листа крановой поправки есть блок `KAVKAZ I` с колонками
  `До обнул. / После обнул. / ИТОГО` по трюмам 1–5 — обнуление судовых
  весов. В файле он пустой (все нули), в модели данных не представлен.
- Даты в файле смешанные: замеры коэффициентов 2024–2025 гг., операции
  выгрузки помечены `5/1/26 12:05`. В макетах взят единый условный
  таймлайн сентября 2026 — тоннажи важны, даты нет.
- Часть строк SOF набрана красным (`INWARD FORMALITIES`,
  `RCVD FREE PRACTIQUE`) — похоже на ручную пометку значимых событий.
  Отдельного признака в данных нет.

## Открытые вопросы к заказчику

1. **Как выводится рабочий коэффициент из истории?** Среднее по
   невыброшенным сходится не для всех режимов. Это суждение оператора или
   есть правило (медиана, последние N замеров, взвешивание по тоннажу)?
2. **Нужен ли `shifting`** как тип крановой операции — в файле его нет.
   И наоборот: нужен ли отдельный тип для **прямого варианта**
   (баржа → OGV, минуя трюмы)?
3. **Делится ли `ИЗ СЕБЯ` по бортам?** В файле — нет, в отличие от
   `В СЕБЯ`. Это свойство операции или просто так сложилось?
4. **Куда идёт скорректированный вес?** Сейчас видно, что только в
   документ. Он где-то сверяется с B/L или с весом принимающего судна?
5. **Один OGV на рейс или несколько?** И может ли один рейс KAVKAZ IV
   обслуживать разные океанские суда?
6. **Нужно ли вести обнуление весов** по трюмам, или блок в файле — рудимент?
7. **Красные строки в SOF** — это категория события или просто выделение?
