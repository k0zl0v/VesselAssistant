# UX-разбор: что видит и чувствует пользователь

> По результатам чтения UI-кода (App.tsx, страницы, 12 компонентов, словари i18n, сервисы). Оценка — глазами уставшего оператора на качающемся судне с небольшим экраном.

## Карта интерфейса

Навигация одноуровневая: три таба сверху + переключатель языка EN/RU справа.

- **«Рейсы»** (`VoyagePage`) — главный рабочий экран. Селект выбора рейса, кнопки «Новый рейс» и «Заполнить демо (KAVKAZ IV)». Карточка рейса: итоги (На борту / Погружено / Выгружено / Свободно 100% / Свободно 98%), экспорт XLSX, «Закрыть рейс». Два саб-таба: **Трюмы** (таблица из 10 колонок; строка трюма раскрывается в LIFO-стек партий с действиями «+ Добавить партию» и «↓ Выгрузить») и **SOF** (таблица событий + форма).
- **«Справочники»** (`ReferencePage`) — длинный скролл из 5 секций: суда, трюмы, краны, крановые поправки (таблица коэффициентов + калькулятор), грузы. Инлайн-формы добавления.
- **«Инструменты»** (`ToolsPage`) — бэкап/восстановление, импорт из Excel, аудит-лог (последние 200 записей с человекочитаемым диффом «поле: было → стало»).

## Что сделано хорошо (важно для работы в море)

- **Полный offline** — ни одного сетевого вызова, SQLite локально.
- **Автосохранение by design** — кнопки «Сохранить» нет: каждое действие сразу транзакционно пишется в БД. Пропало питание — состояние консистентно (транзакции с откатом).
- **LIFO навязан интерфейсом** — оператор физически не может списать с нижней партии и нарушить таможенный учёт.
- **Итоговые поля нельзя править руками** — целостность расчётов защищена архитектурно.
- **Автоматический аудит** SQL-триггерами + удобный просмотрщик изменений.
- **Настоящий двуязычный UI** (~190 ключей, мгновенное переключение, выбор запоминается).
- **Демо в один клик** — идемпотентный сидер KAVKAZ IV, новичок может «потыкать» без страха.
- **Staged-импорт Excel** — превью → «Применить»/«Отмена», а не слепая запись.
- **Защита бэкапом**: восстановление предупреждает «СОТРЁТ все текущие данные», датированные имена файлов.
- **Разумные дефолты**: сегодняшняя дата, SF 1.25, шаблоны формулировок SOF (17 категорий с автозаполнением описания).
- **Перегруз (AT-05)**: попытка превысить 98% → предупреждение с суммой превышения и явное подтверждение; при отказе введённые значения сохраняются — можно поправить и повторить.

## Слабые места (реальные, из кода)

Главная системная проблема: **нет слоя прощения человеческих ошибок**. Данные защищены отлично, а человек — нет.

1. **Нет undo, edit и почти нет delete.** Опечатался в тоннаже партии — исправить нельзя: у лотов, справочников и коэффициентов нет ни редактирования, ни удаления. Для журнала, который ведут руками на качке, это критично.
2. **«Закрыть рейс» — необратимость в один клик**: без подтверждения, метода reopen в `VoyageService` нет.
3. **Молчаливые падения.** На `VoyagePage` ошибки действий вне форм («Закрыть рейс», «Заполнить демо», переключение рейса) никем не ловятся — unhandled rejection, пользователь не получает никакой обратной связи.
4. **Ошибки сервисов — сырые английские строки с UUID.** Русскоязычный оператор при нехватке груза видит `Insufficient cargo in hold 3f2a…: X tons short` вместо «В трюме №3 не хватает X т».
5. **Мелкие поля с плейсхолдерами вместо лейблов** (SF — 5rem, тонны — 7rem, всё в одну строку): после ввода не видно, какое поле что означает; на качке и мелком экране — промахи.
6. **Время SOF — текстовые поля с regex-паттерном** (не `type="time"`): ошибку формата пользователь узнаёт только из нативного тултипа браузера при сабмите.
7. **Удаление SOF-события — без подтверждения** (кнопка ✕).
8. **Нет визуализации трюмов** — только таблица чисел; заполненность не показана ни баром, ни цветом. Отрицательный остаток подсвечен только цветом (красным) — на солнце/для дальтоника может потеряться.
9. **Экспорт XLSX не сообщает об успехе** — кнопка мигнула «Экспорт…» и всё; проверить, записался ли файл, можно только в Finder/Explorer. При этом бэкап успех показывает — непоследовательно.
10. **Импорт завершён → «Идентификатор рейса: {UUID}, откройте вкладку Рейсы»** — сырой UUID и ручной переход вместо автоматического открытия рейса.
11. **Крановый калькулятор оторван от работы**: живёт в Справочниках, результат никуда не сохраняется и в операции не попадает.
12. **`window.confirm` для решения о перегрузе** — нативный диалог без контекста (вместимость, текущий остаток), на автомате легко нажать OK.
13. **Нет портов в форме нового рейса**, хотя домен и импорт их поддерживают.
14. **Нет тёмной темы и print-стилей** — ночная вахта со слепящим белым экраном; печать документов идёт только через XLSX.
15. **Мелочи**: раскрыть можно только один трюм за раз (не сравнить два бок-о-бок); детектор протеина срабатывает по подстроке `'wheat'` — груз «ПШЕНИЦА» поле протеина не получит; нет горячих клавиш и поиска; аудит ограничен 200 записями без пагинации.

## Идеи улучшений (приоритезированы по цене/пользе)

### Дёшево и сразу полезно
| Идея | Решает |
|---|---|
| Confirm-диалог на «Закрыть рейс» + метод `reopen()` | №2 |
| Показ ошибок фоновых действий в тосте/баннере | №3 |
| Сообщение об успехе экспорта с путём к файлу | №9 |
| Confirm на удаление SOF-события | №7 |
| `<input type="time">` в форме SOF | №6 |
| Лейблы над полями вместо плейсхолдеров, крупнее поля | №5 |
| Порты погрузки/выгрузки в форме рейса | №13 |
| После импорта — автоматически открыть рейс | №10 |

### Средняя сложность
| Идея | Решает |
|---|---|
| Коды ошибок сервисов (по образцу `OVERLOAD:<json>`) + маппинг на `t()`-ключи с номером трюма вместо UUID | №4 |
| Прогресс-бар заполнения трюма (зелёный/жёлтый/красный) | №8 |
| Кастомный модал перегруза с деталями (вместимость, остаток, превышение) | №12 |
| Edit/delete последнего лота и справочников как «корректировка» — аудит-триггеры уже всё запишут | №1 |
| Тёмная тема через CSS-переменные (палитра уже на custom properties) | №14 |
| Кнопка «использовать в выгрузке» из кранового калькулятора | №11 |

### Дорого, но меняет класс продукта
| Идея | Решает |
|---|---|
| Undo последней операции (компенсирующая транзакция на базе audit_log) | №1 |
| Схема судна с трюмами и слоями LIFO (визуальный стек партий) | №8 |

## Итоговая оценка UX

Для MVP это добротный «инструмент инженера»: быстрые инлайн-формы, честные данные, сильная защита целостности на уровне БД, правильные дефолты. Слабое звено — прощение человеческих ошибок: undo, редактирование, подтверждения необратимых действий и локализованные понятные ошибки. Для судового ПК и уставшего оператора именно это — главный риск и главное направление следующей итерации.
