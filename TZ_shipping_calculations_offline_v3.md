# Техническое задание на разработку офлайн-приложения для расчётов погрузки/разгрузки и оформления судовой документации

Версия: 3.0, актуализировано по уточнениям заказчика

Основано на анализе файла: `Kavkaz IV_ Load St Plan+SOF.xlsx`. Название `KAVKAZ IV` рассматривается как пример из исходного шаблона; в системе оно должно быть заменяемым параметром судна.

## 1. Назначение системы

Система должна заменить ручное ведение Excel-шаблона локальным офлайн-приложением, которое работает на компьютере судна без постоянного подключения к интернету, хранит рейсы, суда, трюмы, грузы, операции, автоматически рассчитывает остатки/свободное место и формирует документы типа:

- Load/Stowage Plan;
- OGV / operational goods-vessel log;
- Crane correction;
- Statement of Facts / Standard Time Sheet.

Предметная область: судоходство, перевалка/трансшипмент, погрузка/выгрузка на рейде или в порту, оформление ежедневных и итоговых документов.


## 1.1. Ключевое архитектурное требование: offline-first

Приложение должно быть спроектировано как **offline-first desktop application**. Основной сценарий эксплуатации — работа на судне или в порту при нестабильном либо отсутствующем интернет-соединении.

| Параметр | Требование |
|---|---|
| Основной режим | Полностью автономная работа на одном рабочем месте без backend и без постоянного интернета. |
| Хранение данных | Локальная база данных или локальный файл проекта на устройстве пользователя. |
| Расчёты | Выполняются внутри приложения, без обращения к внешнему серверу. |
| Генерация документов | Выполняется локально: XLSX, PDF, при необходимости DOCX. |
| Обновления | Не должны блокировать работу программы. Обновление возможно вручную или при наличии связи. |
| Синхронизация | Не входит в обязательный MVP. Должна быть предусмотрена архитектурно как будущий опциональный модуль. |

Требование к формулировке для договора/ТЗ:

```text
Система должна работать полностью автономно на локальном компьютере пользователя без необходимости подключения к серверу или постоянного доступа к интернету.
```

## 2. Итоги анализа исходного Excel-файла

| Лист | Смысл и роль в системе |
|---|---|
| `SOF` | Statement of Facts / Standard Time Sheet: карточка судна, порт, груз, события по датам и времени, ожидания, операции, формальности, итоговые подписи. Формул нет; это документально-журнальная часть. |
| `KAVKAZ IV` | Основной расчётный лист Load/Stowage Plan: данные судна, порты, грузы, трюмы, SF, объёмы трюмов, загружено, выгружено, остаток, свободное место при 100% и при 98% заполнения, проценты пустого объёма, суточный итог. Название листа/судна не должно быть жёстко зашито: пользователь должен иметь возможность указать любое название основного судна. |
| `OGV` | Операционный лист по судам/баржам и трюмам: что и сколько погружено/выгружено, распределение по трюмам №1-7, начало/окончание, остатки к загрузке по sequence plan. Лист/модуль `OGV` должен получать доступ к данным основного листа/модуля судна и брать из него доступный груз для загрузки в судно на `OGV`. |
| `CRANE CORR.` | Справочник/расчёт поправок по кранам: коэффициенты по типам операции, бортам, кранам, датам/судам; расчёт поправленного веса по данным весов. |

| Сущность | Описание |
|---|---|
| Vessel / Судно | Название, флаг, владелец, IMO при наличии, рейс, порты, набор трюмов, вместимость трюмов. |
| Voyage / Рейс | Конкретная операция судна: loading port, discharging port, даты, груз, SOF, план и фактическое исполнение. |
| Hold / Трюм | Номер трюма, геометрическая вместимость в м³, допустимый процент заполнения, текущий груз и тоннаж. |
| Cargo / Груз | Название груза, protein/качество, единицы измерения, допустимые ограничения. SF/stowage factor задаётся не только на уровне груза, но может отличаться по каждому трюму и каждому судну. |
| Cargo lot / Партия груза | Отдельная партия груза, загруженная от конкретного судна-источника/баржи в конкретный трюм или набор трюмов, с датой/временем и порядком погрузки. |
| Cargo layer / Слой груза | Расчётный слой внутри трюма. Слой соответствует партии или части партии и используется для таможенного правила выгрузки сверху вниз. |
| Coaster/Barge | Судно-источник или приёмник, даты подхода, операции all fast/cast off, откуда/куда грузится. |
| Operation | Событие погрузки/выгрузки/ожидания: дата, время от/до, описание, тип операции, объём/тоннаж, трюмы, кран. |
| Crane correction | Коэффициент корректировки веса по крану, типу операции, стороне борта, дате/судну. |
| Statement of Facts | Хронологический журнал событий рейса для печатной формы и подписания. |

### 3.1. Уточнённые параметры груза

| Параметр | Требование |
|---|---|
| `Protein` | Количество протеина в пшенице. Должны поддерживаться значения 10.5%, 11.5%, 12.5%, 13.5%. Значение выбирается для партии/груза и выводится в документах. |
| `SF` / Stowage Factor | Удельный погрузочный объём. Значение SF может быть разным в каждом трюме и у разных судов. Нельзя считать SF единым глобальным значением для всего рейса. |
| `FillPercent` | Для текущего MVP используется только 98% заполнения трюмов. 100% может использоваться только как справочный/контрольный расчёт, если требуется повторить Excel. |

## 4. Входные данные

1. Справочник судов: название, флаг, владелец, вместимость трюмов, количество трюмов, стандартные коэффициенты заполнения.
2. Справочник грузов: название, характеристики качества, protein, правила совместимости по трюмам. Для пшеницы должны поддерживаться значения protein: 10.5%, 11.5%, 12.5%, 13.5%.
3. Рейс: loading/discharging port, voyage number, даты прибытия, NOR, бертовка, начало/окончание грузовых операций, отход.
4. План погрузки: распределение партий по трюмам, судно-источник/приёмник, груз, protein, SF для конкретного трюма/судна, тоннаж, трюм назначения, expected/actual quantity, дата/время погрузки, порядковый номер партии/слоя.
5. Факт операций: дата, время, описание, трюм, кран, количество, статус: loading, discharging, shifting, waiting, formalities, bunkering и т.д.
6. Коэффициенты кранов: тип операции, сторона борта, номер крана, дата/судно, коэффициент, вес по весам.
7. Данные для SOF: события в хронологическом порядке, периоды простоя/работы, формальности, комментарии агента/капитана.

## 5. Расчётная логика

| Расчёт | Правило |
|---|---|
| Итог загружено по трюму | `LoadedHold[h] = сумма всех партий, назначенных в трюм h`. |
| Выгружено из трюма | `DischargedHold[h] = сумма операций выгрузки/перевалки из OGV по соответствующему трюму`. |
| Остаток в трюме | `RemainHold[h] = LoadedHold[h] − DischargedHold[h]`. |
| Расходование слоёв при выгрузке | При выгрузке из трюма груз должен убывать слоями сверху вниз: последняя загруженная партия считается верхним слоем и выгружается первой. Расчётный принцип — LIFO по партиям внутри каждого трюма. |
| Остаток по партии/слою | `RemainLot[l] = LoadedLot[l] − DischargedFromLot[l]`, где `DischargedFromLot` распределяется автоматически по LIFO-очереди трюма. |
| Тоннажная вместимость при 100% | `CapacityTons100[h] = HoldVolumeM3[h] / SF[h,cargo,vessel]`. |
| Свободное место при 100% | `EmptySpace100[h] = CapacityTons100[h] − RemainHold[h]`. |
| Тоннажная вместимость при допустимом заполнении | `CapacityTonsAllowed[h] = HoldVolumeM3[h] × 0.98 / SF[h,cargo,vessel]`. Для MVP используется только 98% заполнения. |
| Свободное место при 98% | `EmptySpaceAllowed[h] = CapacityTonsAllowed[h] − RemainHold[h]`. Это основной расчёт доступного места. |
| Итог свободного места | `TotalEmpty = сумма только положительных EmptySpace по трюмам`; отрицательные значения не увеличивают доступное место. |
| Процент пустого объёма | `EmptyVolumePercent[h] = 100 − LoadedVolume[h] / HoldVolumeM3[h] × 100`. |
| Суточный итог | `DailyTotal = CurrentOnBoard − PreviousOnBoard` либо сумма операций за сутки, в зависимости от режима отчёта. |
| Поправка по крану | `CorrectedWeight = ScaleWeight / CraneCoefficient`. |
| Остаток по sequence plan | `RemainToLoadByHold[h] = PlannedByHold[h] − ActualLoadedByHold[h]`. |


### 5.1. Таможенное правило выгрузки слоями сверху вниз

При выгрузке из основного судна система должна учитывать не только общий остаток по трюму, но и происхождение груза по партиям/судам-источникам. Для целей таможенного учёта груз в каждом трюме должен списываться **сверху вниз**.

Правило:

```text
Внутри каждого трюма партии формируют стек слоёв.
Последняя загруженная партия находится сверху.
При выгрузке первой списывается верхняя партия.
Если выгрузка превышает остаток верхней партии, остаток списывается со следующей нижней партии.
```

Пример:

```text
1. Судно DIANA MARIA загрузило в основное судно 1600 т.
2. Затем судно VELES загрузило 1200 т.
3. Партия VELES находится выше партии DIANA MARIA.
4. При выгрузке первые 1200 т должны быть списаны с VELES.
5. Только после полного списания VELES начинается списание с DIANA MARIA.
```

Алгоритм списания для одного трюма:

```text
function dischargeFromHold(holdId, dischargeQty):
    layers = getRemainingLayers(holdId).sortBy(load_sequence DESC)
    qtyLeft = dischargeQty

    for layer in layers:
        if qtyLeft <= 0:
            break

        writeOff = min(layer.remaining_tons, qtyLeft)
        layer.remaining_tons -= writeOff
        createDischargeAllocation(operationId, layer.id, writeOff)
        qtyLeft -= writeOff

    if qtyLeft > 0:
        raise Error("Недостаточно груза в трюме для выгрузки")
```

Система должна хранить результат такого распределения, чтобы в любой момент можно было показать:

- сколько груза каждого судна-источника осталось на борту;
- какие партии были списаны при конкретной операции выгрузки;
- какой слой находится сверху в каждом трюме;
- расхождения между физическим остатком, документальным остатком и таможенным учётом.

### 5.2. Связь основного листа судна и OGV

Модуль `OGV` не должен быть независимой таблицей ручного ввода. Он должен использовать данные из основного модуля судна, который в исходном Excel назывался `KAVKAZ IV`, а в программе должен называться по выбранному пользователем основному судну.

Требование:

```text
OGV берёт доступный груз, остатки, трюмы, SF, protein и слои из основного модуля судна.
При операции загрузки/выгрузки в OGV система должна автоматически уменьшать/увеличивать соответствующие остатки в основном модуле и пересчитывать Load/Stowage Plan.
```

Для пользователя это должно выглядеть как единая база данных рейса, а не как несколько разрозненных Excel-листов. Изменение в `OGV` должно отражаться в основном плане судна, а изменение плана/остатков основного судна должно быть доступно для выбора и контроля в `OGV`.

### 5.3. Округление

Все расчётные значения, которые отображаются пользователю или экспортируются в документы, должны округляться до **трёх знаков после запятой**.

Внутреннее хранение допускается с большей точностью, но печатные формы, таблицы и Excel/PDF-экспорт должны использовать единый формат:

```text
0.000
```

## 8. Проверки и бизнес-правила

1. SF по грузу обязателен для расчётов empty space. Деление на ноль запрещено.
2. Тоннаж в трюме не должен превышать допустимую вместимость при выбранном `FillPercent` без предупреждения/подтверждения.
3. `RemainHold` не должен быть меньше нуля; если отрицательный — подсветка как ошибка расхождения плана и факта.
4. События SOF должны идти по времени; пересечения интервалов для одного рейса требуют предупреждения.
5. Время `24:00` должно корректно интерпретироваться как конец суток, а не как некорректное время.
6. Операция с краном не может использовать коэффициент, не действующий для даты/типа операции/стороны борта.
7. Закрытый рейс доступен только для просмотра и экспорта; изменения — через корректировочный акт или новую ревизию.
8. Все ручные правки итоговых значений запрещены: итоговые поля должны быть только вычисляемыми.
9. Название основного судна является параметром рейса/справочника судов. Запрещено использовать `KAVKAZ IV` как жёстко зашитое значение в коде, шаблонах экспорта или названиях сущностей.
10. При выгрузке из трюма списание по партиям выполняется только по принципу LIFO: верхний слой, то есть последняя загруженная партия, списывается первым.
11. Пользователь не должен вручную выбирать, с какой нижней партии списать выгрузку, если верхние партии ещё имеют остаток. Ручная корректировка допустима только отдельной операцией с причиной и записью в audit trail.
12. Операция выгрузки не может списать больше, чем суммарный остаток всех слоёв в выбранном трюме.
13. Для MVP допустимая заполняемость трюмов фиксируется как 98%. Изменяемый FillPercent можно предусмотреть архитектурно, но не реализовывать в первой версии.
14. SF должен храниться и использоваться на уровне конкретного трюма/партии/судна. Если в одном рейсе разные трюмы имеют разный SF, расчёты должны выполняться отдельно по каждому трюму.
15. Все результаты в интерфейсе и документах округляются до 3 знаков после запятой.
16. Вводимые пользователем поля не должны содержать формул. При импорте Excel формулы в ячейках ввода должны быть заменены на рассчитанные значения или проигнорированы согласно правилам импорта.
17. OGV не должен дублировать данные вручную: доступный груз для операций OGV должен выбираться из остатков основного судна.

## 10. Интерфейсы пользователя

- Экран рейса: карточка судна/портов, статус, текущие итоги, предупреждения.
- Экран трюмов: таблица `Hold №`, `cargo`, `protein`, `SF`, `volume`, `loaded`, `discharged`, `remain`, `empty space 98%`, `percent empty`. SF редактируется по каждому трюму/партии.
- Экран операций OGV: ввод партий/операций по трюмам с быстрым копированием строк и проверкой итогов. OGV должен выбирать доступный груз из основного судна и автоматически обновлять остатки основного Load/Stowage Plan.
- Экран SOF: хронологический журнал событий с шаблонами типовых формулировок и автозаполнением from/to.
- Экран crane correction: выбор операции, крана, стороны борта, коэффициента и расчёт corrected weight.
- Экран документов: генерация, предпросмотр, экспорт, история ревизий.
- Экран слоёв груза: визуальное отображение порядка партий в каждом трюме сверху вниз, остатки по суднам-источникам и история списания при выгрузке.

Backend API на этапе MVP не требуется. Внутри приложения должны быть выделены независимые локальные модули, чтобы бизнес-логика не была смешана с интерфейсом.

| Модуль | Назначение |
|---|---|
| `VoyageService` | Создание, копирование, закрытие рейса; получение карточки рейса и итогов. |
| `CargoLotService` | Добавление и изменение партий груза, распределение по трюмам. |

| `OperationService` | Регистрация операций погрузки/выгрузки/ожидания и пересчёт связанных итогов. |
| `OgvService` | Получение доступного груза из основного судна, создание OGV-операций, обратное обновление остатков и слоёв в основном Load/Stowage Plan. |

Для будущей синхронизации допустимо заранее проектировать внутренние методы так, чтобы их можно было позднее обернуть в REST/GraphQL API, например:

Важно: в MVP эти методы выполняются локально и не требуют сетевого соединения.

### 13.1. Целевая схема работы

```text
Пользовательский интерфейс
        ↓
Локальные сервисные модули
        ↓
Calculation Engine
        ↓
SQLite / локальный файл проекта
        ↓
Document Engine
        ↓
XLSX / PDF / DOCX
```

### 13.2. Почему не нужен backend в MVP

Backend не требуется, потому что:

1. Все расчёты выполняются по локальным формулам.
2. Все справочники можно хранить на устройстве.
3. Документы формируются из локальных шаблонов.
4. Основной пользовательский сценарий — работа на одном компьютере на судне.
5. Интернет на судне нестабилен и не должен быть критической зависимостью.

### 13.3. Когда backend может понадобиться позже

Backend можно рассматривать как отдельный этап, если потребуется:

- централизованная база рейсов компании;
- удалённый контроль офиса за текущими операциями;
- синхронизация между несколькими рабочими местами;
- централизованное управление пользователями;
- облачные бэкапы;
- обмен данными с ERP, портовыми системами или агентскими сервисами.

Для MVP эти функции не обязательны.

## 14. Решённые уточнения и оставшиеся открытые вопросы

### 14.1. Зафиксированные уточнения

1. `Protein` — количество протеина в пшенице. Поддерживаемые значения: 10.5%, 11.5%, 12.5%, 13.5%.
2. `SF` — Stowage Factor, удельный погрузочный объём. Значение SF может быть разным в каждом трюме и у каждого судна.
3. Округление расчётных значений — до трёх знаков после запятой.
4. Расчёт laytime/demurrage и расширенные SOF-правила можно добавить позже; в MVP не включать.
5. Заполняемость трюмов для MVP — только 98%.
6. Желательно повторение Excel-шаблона; улучшенный интерфейс, графики и более современный дизайн можно добавить как альтернативный режим, не ломая привычный Excel-вид.
7. В ячейках/полях ввода данных не должно быть формул. Формулы должны быть вынесены в расчётный модуль.
8. `OGV` должен иметь доступ к данным основного модуля судна и брать груз именно оттуда для операций на `OGV`.

### 14.2. Оставшиеся открытые вопросы

1. Нужно определить формат обмена данными между судном и офисом: полный файл проекта, экспорт отчёта или будущая синхронизация.
2. Нужно подтвердить, требуется ли LIFO-списание слоями строго отдельно для каждого трюма или также на уровне всего судна при смешанных выгрузках без указания трюма.

## Приложение A. Контрольная формула расчёта Empty Space

Для каждого трюма `h` и груза `c`:

```text
CapacityTons98[h]    = HoldVolumeM3[h] × 0.98 / SF[h,c,vessel]
EmptySpace98[h]      = CapacityTons98[h] − RemainHold[h]
TotalEmpty98         = SUM(max(0, EmptySpace98[h]))

All displayed/exported values are rounded to 3 decimal places.
```

## Приложение B. Контрольная логика списания слоёв

Для каждого трюма `h` партии сортируются по порядку погрузки:

```text
Layers[h] = SORT(cargo_layers WHERE hold_id = h AND remaining_tons > 0 BY load_sequence DESC)
```

При выгрузке `Q` тонн из трюма `h`:

```text
qtyLeft = Q
for layer in Layers[h]:
    writeOff = min(layer.remaining_tons, qtyLeft)
    layer.remaining_tons = layer.remaining_tons - writeOff
    qtyLeft = qtyLeft - writeOff
    save discharge allocation
    if qtyLeft == 0: stop

if qtyLeft > 0:
    operation is invalid
```

Контрольный пример:

| Порядок | Судно-источник | Загружено | Положение слоя |
|---:|---|---:|---|
| 1 | DIANA MARIA | 1600 т | Нижний слой |
| 2 | VELES | 1200 т | Верхний слой |

Выгрузка 500 т должна уменьшить только VELES:

| Судно-источник | Остаток после выгрузки 500 т |
|---|---:|
| VELES | 700 т |
| DIANA MARIA | 1600 т |

Следующая выгрузка 900 т должна списать 700 т с VELES и 200 т с DIANA MARIA.
